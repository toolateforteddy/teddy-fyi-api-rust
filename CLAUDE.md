# teddy-fyi-api-rust

The sync backend and source of truth for two products: **teddy.fyi** (household
grocery and todo lists, iOS and Android) and **ScribbleRoute** (ScribbleKeep and
ScribbleBox, the tablet apps in the `toybox` repo). One Rust service, one Postgres,
one Redis, two hostnames — `api-rust.teddy.fyi` and `api.scribbleroute.com` — and a
plan to split it in two that is already written down and not yet started.

This file is how to *work* in the repo. Three other places carry the rest, and none
of them repeats this one:

- **`README.md`** — the API contract: every endpoint, every request and response
  body, every environment variable, and the `dev-auth` story in full. Read it before
  changing a wire format.
- **`AGENTS.md`** — deployment and `k8s/`, and the index of planned work that already
  has a written spec. Read it before touching a manifest or designing anything in one
  of those areas.
- **`context/`** — one file per topic, dated. The decisions themselves.

## Working on several tasks at once

Tasks run in parallel git worktrees under `.claude/worktrees/`, one per
conversation (the directory is gitignored — the branches are pushed, the checkouts
are not). The rules exist because worktrees outlive their PRs otherwise, and new
work silently starts from a base that is several merges old.

**One worktree = one task = one PR, and it dies at merge.**

- **Starting new work.** Branch from the remote, never from whatever HEAD happens to
  be: `git fetch origin && git switch -c claude/<task> origin/main`. The
  `SessionStart` hook fetches and warns when the tree is behind, but branching from
  `origin/main` is what makes staleness impossible.
- **Work already in progress.** If `main` moves under you, bring it in. Unlike the
  `toybox` sibling, PRs here land as **merge commits**, not squashes, and branches
  already carry `Merge origin/main into <branch>` commits — so a merge is the house
  style and `git branch --merged` tells the truth about what has landed. Rebase a
  branch nobody else has pulled if you prefer a clean diff; never rebase one that is
  already under review.
- **After the PR merges.** Remove the worktree and delete the branch.
- **Never reuse a worktree for an unrelated task.** If a session starts in a worktree
  whose branch is already merged, branch fresh from `origin/main` before touching
  anything.

## The repo

One binary (`src/main.rs`), ~31k lines of Rust in `src/`, of which ~14k are tests.
The layout rule is strict and has its own constraint below: **no `mod.rs`** — a
parent declares its children from a sibling file, so `routes.rs` sits beside
`routes/`, and an entry file carries declarations only.

| Module | What it is |
| --- | --- |
| `src/routes/sync` | **The service.** ~18k lines: the `POST /api/sync` reconciliation, the SSE stream, and per-table handling for todo, grocery, config, drawing and device rows. Everything else is around it. |
| `src/routes/ai` | Gemini categorisation and todo icons, with the per-user and global budget counters and the kill switch. |
| `src/routes/lists` | Collaborative list membership and invites. |
| `src/routes/devices` | Device registration and the per-account cap. |
| `src/routes/user` | Account read and `DELETE /api/user/data` — the erasure path. |
| `src/auth` | Google ID-token validation, the client-ID catalogue, JWT minting and refresh, the request middleware, device pairing (`device.rs`), and `dev_bypass.rs`. |
| `src/dao`, `src/models` | Configs and drawings — the ScribbleRoute half — which are stored per device rather than per row-version. |
| `src/guardrails` | Tower layers bounding what one client or one bad request can cost: body size, concurrency, timeouts, panic catching. |
| `src/rate_limit` | The per-IP buckets on `/auth/*`, and the tighter one on `/auth/device/start`. |
| `src/observability` | Health and readiness, the DB-health circuit, HTTP metrics, the Prometheus exporter. |
| `src/jobs` | The reapers: stale users, device authorizations, list invites. Run as subcommands from `k8s/user-reaper.yaml`. |
| `src/db.rs` | Pool configuration, and `sqlx::migrate!` at boot — see constraint 3. |
| `migrations/` | Timestamped SQL, applied by every process at startup. Append-only. |
| `.sqlx/` | Committed query descriptors. Regenerated by `make prepare`, never by hand. |
| `k8s/` | The GKE manifests, applied by `deploy.yml` on every merge to `main` (`AGENTS.md`). |

Two things about identity that will bite before anything else does. The same person
is named two ways — the raw Google subject keys `users`, `sessions` and every
todo/grocery table, while `parse_or_hash_uuid(sub)` keys `configs`, `drawings` and
`devices` — and a token carries a `product` claim that decides which sync scopes it
may ask for (`src/routes/sync/scope_auth.rs`). Read
`context/2026-09-05_user_identity_derivation.md` before writing any endpoint that
takes a user identifier from a request body.

## Building and testing

```bash
make dev            # Neon branch database + local Redis + hot reload, with dev-auth
make test           # production feature set -- what CI runs
make test-dev-auth  # the other half of the matrix
make prepare        # regenerate .sqlx/ after touching any sqlx::query!
cargo clippy -- -D warnings
```

Four things here are not obvious and each has cost somebody a red CI run:

- **`cargo clippy -- -D warnings`, without `--all-targets`.** That is CI's exact
  command, and it lints the binary, not the test code. Adding `--all-targets` today
  reports ~28 findings in tests that CI has never gated on — so a "cleanup" driven by
  it is a large diff nobody asked for, and it is not the check to reproduce a failure
  with.
- **Both feature configurations, always.** `dev-auth` compiles in the `mock.` login
  bypass and each configuration compiles tests the other does not. CI runs clippy and
  the suite twice for this reason. A change anywhere near `src/auth/` needs both.
- **`SQLX_OFFLINE=true` everywhere except one step.** The `query!` macros are checked
  against the committed `.sqlx/` descriptors rather than a database, which is what
  lets CI and the Dockerfile build without Postgres — and which means a descriptor
  that no longer matches the schema compiles green right up until production. If you
  add, remove or edit a `sqlx::query!`, run `make prepare` against a migrated
  database and commit `.sqlx/`. CI's "Check SQLx Offline Cache" step is the thing
  that catches you.
- **The tests need a real Postgres.** Around 190 of the ~350 cases are
  `#[sqlx::test]`, which creates a database per test and applies `migrations/` to it.
  Without a server they do not skip, they fail. Redis is the opposite and worse: tests needing it print `SKIP` and
  pass, so a suite run without Redis is green on cases that never ran.

## Validating in a cloud container

`./validate.sh` is the entry point wherever you are. It runs the strongest gate the
machine allows and says which one that was.

```bash
./validate.sh              # start what is missing, run the full gate
./validate.sh --full       # require a database; fail rather than fall back
./validate.sh --no-db      # clippy and the constraints only
./validate.sh --no-start   # use what is already up, start nothing
```

**A container can run the whole CI gate, and this is the thing worth knowing.**
Unlike the `toybox` sibling — where a missing SDK or a blocked `dl.google.com` makes
the real build impossible and the fallback is genuinely weaker — nothing here is
out of reach:

- `crates.io` is reachable through the proxy, so `cargo fetch`, `clippy` and `test`
  all work. (`static.crates.io` answers 403 to a bare `curl`; that is the proxy
  refusing a directory fetch, not a blocked host. `cargo fetch --locked` succeeding
  is the real test.)
- **Postgres and Redis are installed on the standard image and simply not running.**
  `service postgresql start` and `redis-server --daemonize yes` are all it takes, and
  `validate.sh` does both for you when it is running as root. A Postgres started this
  way needs the CI credentials to match the default `DATABASE_URL`
  (`postgres://postgres:password@localhost:5432/test_db`); the script sets them.

So "I could not run the tests in this container" is almost never true here. What a
container genuinely cannot reach is Neon, GCP and the deployed service — so `make
dev` (which provisions a Neon branch through `neonctl`) is a laptop command, and
anything about a live rollout has to be read from CI, not reproduced.

The one gap that survives is `cargo sqlx prepare --check`, which needs `sqlx-cli`
installed (`cargo install sqlx-cli --locked --version ^0.8 --no-default-features
--features rustls,postgres`, a few minutes). `validate.sh` skips it with a note when
the binary is absent; CI does not skip it.

## Hard constraints

Five rules bind all work here. Each has a consequence no lint reports —
impersonation in production, a rollout that will not boot, a copy of a child's
drawing that no erasure path can delete. `scripts/check_constraints.sh` is the
tripwire for all five, runs in every `validate.sh` mode, and is not run by CI at all.

1. **The `mock.` login bypass never ships.** `src/auth/dev_bypass.rs` mints a session
   for whatever `user_id` a request names, without validating anything. It is gated
   at *compile* time — deliberately, because it used to be gated on `COOKIE_DOMAIN`
   being empty, which meant one manifest edit away from total impersonation. Keep
   `dev-auth` off the default feature list and out of the Dockerfile, `deploy.yml`
   and `k8s/`. The two start-up assertions that refuse to boot a dev-auth binary
   holding real client IDs, and a normal binary holding none, are part of the same
   gate: do not soften them into warnings.

2. **No `mod.rs`, and module entry files stay declarative.** `routes.rs` beside
   `routes/`, `auth.rs` beside `auth/`. An entry file holds `pub mod` and `pub use`
   and, at most, `#[cfg(test)] mod tests;` — never a handler and never a test body.
   This is a standard the repo has held from the start; it is cheap to keep and
   expensive to restore.

3. **A committed migration is immutable.** `db::init_postgres` runs
   `sqlx::migrate!("./migrations")` on *every* boot, and sqlx checksums what it has
   already applied. Editing a migration that has run in production means the next
   rollout refuses to start — after the image is pushed, with the old pods already
   going away. Add a new timestamped migration instead. Note also that split plan
   §1.2 puts a no-new-migrations constraint on Phases 2–3; read
   `context/2026-09-05_scribbleroute_backend_split.md` before touching `migrations/`
   or `src/db.rs`.

4. **Secrets live in GCP Secret Manager, never in the repo.** What `k8s/` holds is
   the wiring, and adding one secret-backed variable is three edits to
   `api-rust.yaml` (`AGENTS.md` has them). A literal in a manifest is a secret
   published to everyone who can read the repo, and rotating it becomes a commit.

5. **User data never reaches the logs.** Cloud Logging is reachable by neither
   `DELETE /api/user/data` nor `jobs::reap_stale_users`, so a log line carrying a
   request body, a config value or a drawing is a copy of user data that no erasure
   path can ever delete. `src/routes/sync/tests/log_hygiene.rs` asserts on the
   *emitted* tracing events rather than the call sites; when it fails, the fix is the
   log line, never the test. Identifiers are hashed (`LOG_HASH_SALT`) for the same
   reason.

One more thing that is not a constraint but behaves like one: **most tunables are
unset in production.** The code reads about forty environment variables and the
manifests set eleven, so for everything else the compiled-in default *is* the
production value. Changing a default in Rust is changing prod.
