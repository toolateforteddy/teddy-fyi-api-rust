# The identity model: one opaque user id, provider named explicitly

*Written 2026-09-05. Status: **design, not built.** Nothing described here exists in the code.*

Companion docs: [`2026-09-05_user_identity_derivation.md`](2026-09-05_user_identity_derivation.md)
records what is true **today** and why it is a migration rather than a refactor;
[`2026-09-05_scribbleroute_backend_split.md`](2026-09-05_scribbleroute_backend_split.md) is the
split this work rides along with. Read the derivation note first — this note assumes it and does
not repeat its evidence.

---

## The decision

`users.id` becomes an **opaque surrogate UUID**, generated by us, derived from nothing. The
provider's subject stops being an identity and becomes an attribute: two columns on `users`,
`provider` and `subject`, unique together. Every table in the service keys the surrogate. There
is exactly one user identity again, and it is a UUID everywhere.

```sql
users (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  provider   TEXT NOT NULL,          -- 'google' | 'apple' | …
  subject    TEXT NOT NULL,          -- the provider's `sub`, verbatim
  email      TEXT,                   -- provider-asserted; may be absent or a relay address
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (provider, subject)
)
```

Sign-in is one lookup on `(provider, subject)` and an upsert. There is no join table and no
second hop.

**Accounts are not linked across providers.** One `users` row is one provider identity. This is a
deliberate product decision, not an omission; §4 states what it costs.

## 1. Why the two options in the derivation note are both dead ends

The derivation note offers an HMAC re-key or canonicalising on the raw subject. Both keep the same
equation:

> identity = f(provider subject)

A second identity provider breaks that equation rather than stressing it. Google's `sub` and
Apple's `sub` for one human are unrelated opaque strings, so `f(google_sub)` and `f(apple_sub)`
are two different people as far as every query in this service is concerned. Neither an HMAC nor a
wider column changes that. The only fix is a mapping from provider identity to account — and once
that mapping exists, the derivation has no job left. The mapping *is* the identity.

That is the whole argument. Both of the note's options were designed against a single-IdP world
and should not be revived.

## 2. Why a surrogate UUID and not a namespaced subject

The cheap alternative is a namespaced TEXT id — `google:1234567890`, `apple:001234.abc…` — as
`users.id`. It is a real option and it fixes two things: the collision hazard between providers,
and the `parse_str` sharp edge in the derivation note (a namespaced string is never UUID-shaped).

It was rejected for one reason: **it closes a door that the surrogate keeps open for free.**

Under a namespaced id, the id *is* the provider's identity. If account linking is ever wanted —
today it is not, see §4 — the only way to link is to change one of the two ids, which means
rewriting every foreign key in the database. That is precisely the migration this note exists to
avoid repeating.

Under a surrogate, adding linking later is: create an `identities` table, move `provider` and
`subject` onto it, point it at `users.id`. **No child table is touched, because `users.id` never
changes.** The surrogate costs nothing today and makes that a small change instead of a large one.

A secondary, smaller win is column types. After the split this service's tables are `users`,
`sessions`, `configs`, `drawings`, `devices`, `device_authorizations` and
`device_claim_failures`. Under the surrogate the three UUID columns (`configs.user_id`,
`drawings.user_id`, `devices.user_id`) keep their type and change only their values, while the
TEXT ones narrow to UUID. Under a namespaced id, three indexed UUID columns would widen to TEXT
instead.

Use `gen_random_uuid()` (v4). Time-ordered v7 would give marginally better index locality and is
not worth a `uuid` crate feature change at this scale.

## 3. What the surrogate fixes on the way past

None of these are the reason for the change; all of them come with it.

* **The two identities collapse into one.** The derivation note's section 1 — the same person named
  two ways depending on which table you touch — stops being true. `delete_user_data` no longer has
  to hold both values at once.
* **`find_stale_users` becomes a SQL join.** It currently loads every `devices` row and every
  `users` row and joins them in Rust, because `devices.user_id` is a one-way hash of `users.id`.
  With one id there is a real foreign key and one query.
* **The identifier stops being publicly computable.** `Uuid::new_v5(NAMESPACE_DNS, sub)` is an
  unkeyed function of a subject that is not secret. A `gen_random_uuid()` is a function of nothing.
  This matters most at `POST /auth/refresh`, which takes `user_id` from an **unauthenticated** body:
  the value stops being derivable by anyone who learns a subject. (The refresh token is still what
  authenticates that call — this removes an identifier, not a gate.)
* **Foreign keys become expressible.** `sessions`, `configs`, `drawings`, `devices`,
  `device_authorizations` and `device_claim_failures` can all reference `users(id)`, which is what
  makes `ON DELETE CASCADE` an option for the erase path instead of eleven ordered deletes.

## 4. What "no linking" costs, stated plainly

A person who has signed in with Google and later signs in with Apple lands in a **new, empty
account**. Their drawings still exist, under the other identity, and are invisible to them. There
is no automatic recovery and no merge tool.

This is accepted. The alternative — auto-linking on a matching verified email — is a known
account-takeover vector, and Apple makes it worse rather than better: the email may be a private
relay address, the user may hide it entirely, and it is returned **only on the first
authorization**. Trading a recoverable support problem for a class of takeover bug is a bad trade
at this size.

Two consequences worth designing around when a second provider lands:

* **Do not offer two providers on the same platform.** If a user never sees two buttons, they
  cannot take the wrong one. This is the cheap mitigation and it should be the default.
* **App Store guideline 4.8 may make that impossible on iOS.** Offering a third-party sign-in
  (Google, which the iOS clients already use — `GOOGLE_IOS_CLIENT_IDS` is in the manifest) can
  oblige an app to offer Sign in with Apple alongside it. If that binds, the empty-account path is
  a button in our own UI on the platform where users are likeliest to tap the Apple one out of
  habit. **Open item — confirm before Apple work is scheduled, not after.**

Because there is no merge tool, `email` on `users` earns its place as a diagnostic: it is what lets
someone answer "where did my drawings go" by hand. Keep the existing upsert rule —
`COALESCE(EXCLUDED.email, users.email)` — which never overwrites a stored address with a NULL. That
rule is what preserves an Apple address that arrives once and never again.

## 5. `parse_or_hash_uuid` survives; its identity call sites do not

This function is called on three kinds of input and **only the first is an identity**:

| Input | Lands in | After this change |
| :-- | :-- | :-- |
| the auth subject (`Claims.sub`) | `configs.user_id`, `drawings.user_id`, `devices.user_id` | **gone** — the token carries the surrogate directly |
| `client_id` from the sync request | `configs.client_uuid`, `drawings.client_uuid` | **unchanged** — echo-suppression tag, not identity |
| a client-supplied change id | `configs.id`, `drawings.id` | **unchanged** — and must never be re-derived; clients hold these as primary keys |

So the function stays. What must go is any path that hands it a subject. Rename it to something
that cannot be misread as an identity helper — `parse_or_hash_client_uuid` — so that a future call
on a subject does not typecheck as a sensible thing to write, and pin the absence with a test.

`src/routes/sync/tests/identity.rs` is a characterisation suite whose stated purpose is to fail
when this moves. **It is supposed to go red.** Rewrite it rather than updating its constants: the
new invariants are "no table keys a user by anything derived from a subject" and "the surrogate is
not a function of the subject", which are different assertions from the ones there now.

## 6. The legacy-token shim

Tokens already in the field carry the Google subject in `Claims.sub`. Refresh tokens live seven
days, so there is a window in which both shapes arrive.

The rule is one line and needs no new storage:

> If `claims.sub` parses as a UUID, it **is** the user id. Otherwise look it up:
> `SELECT id FROM users WHERE provider = 'google' AND subject = $1`.

The compatibility mechanism and the multi-provider schema are the same table, which is why this
does not need a flag day, a dual-write build, or a token version claim.

Constraints on it:

* **Lifetime: 30 days** after cutover — comfortably past the seven-day refresh TTL, so no live
  session is severed.
* Newly minted tokens carry the surrogate from the moment of cutover. `Claims.sub` never again
  carries a provider subject; that also stops a correlatable provider identifier riding in a token.
* **Delete it on a date, with a test that pins its removal.** A shim with no expiry is a permanent
  second identity path, which is the thing this note is trying to end.

## 7. The open question that decides the scope

`user_id` is not internal to the server. It is a field of `LoginRequest` and `RefreshRequest`, and
it comes back in `BrowserAuthResponse`. `refresh_handler` looks the session up by
`(user_id, client_uuid)` from an unauthenticated body — and it has to, because refresh token
hashes are Argon2 and therefore salted, so a session cannot be found from the token alone. The id
in that body is load-bearing and cannot simply be dropped.

Meanwhile `poll_handler` returns only `{access_token, refresh_token}` — **a paired tablet is never
told its `user_id` by this service.** So a client either decodes `sub` out of our JWT, or it takes
Google's `sub` from the Google ID token itself. Which one it does decides the size of this change:

* **Reads `sub` from our JWT** → clients pick up the surrogate automatically at the next login or
  refresh, and this is a server-only change.
* **Derives it from the Google ID token** → that client breaks permanently at cutover and needs a
  release *before* the migration, not after.

**This must be checked in the Android and iOS clients before the migration is scheduled.** It is
the one unknown that can turn a server-side change into a coordinated client rollout, and it is
cheap to answer.

## 8. Where this happens: Phase 5 of the split

The derivation note's migration is six steps with a dual-write build in the middle. That shape
exists **only because there is no maintenance window**: clients sync continuously, so rows written
between the backfill and the cutover would be lost — and lost in the worst way, because the client
still holds them locally and re-uploads them as inserts, producing duplicates under
`unique_user_device_config_key` rather than an error anyone would notice.

Phase 5 of the split supplies the window. It already freezes writes and rewrites every row into a
fresh database, so the id mapping is one more transformation in a pass that is happening anyway:
no added column, no dual-write build, no second backfill, and no point of no return beyond the one
the phase already has.

**The rollback does not get worse.** It is `DATABASE_URL` back to the old database, which took no
writes during the freeze, and it reverses both changes together. Rollback granularity here is
per-window, not per-change — which is why the split plan's original "one irreversible change per
window" instinct does not apply. What bundling does cost is complexity in the copy program, which
is real but testable, and cheaper than running the six-step migration separately afterwards.

What the copy program does, per `users` row: mint a UUID, write the `users` row with
`provider = 'google'` and `subject` set to the old id, and rewrite the children through that
mapping. It needs the same Rust-side hash join as `find_stale_users` to find the
`configs`/`drawings`/`devices` rows, because the old derivation cannot be inverted.

**Prerequisites, in order:**

1. Answer §7 for both clients. This and the orphan audit are Phase 0 of the split — cheap, and
   much better answered before a freeze than during one.
2. Run the orphan audit from the derivation note's step 2 — rows whose `user_id` is the hash of no
   surviving `users.id`. `configs` and `drawings` predate the `users` table by one migration, so
   some are expected; a large count makes this a different conversation.
3. The fork happens **first** (split plan Phase 4), because while one binary serves both products
   a re-key of only the ScribbleRoute database would leave it straddling two databases with two
   different id types — this note's own problem in the worst possible place.
4. The target schema arrives with the **new database**, not with the fork (split plan Phase 5
   step 1). The fork keeps this repo's migration files byte-identical while it still points at the
   shared database, or the binary meets a migration history it does not carry and crashloops on
   `VersionMissing`; see the split plan §1.3. So there is still no add-column-and-backfill dance —
   it is a fresh database — but the collapse to `0001_init.sql` is a freeze-time step.
5. The shim in §6 ships with the fork and is tested **before** the freeze. It is code, not schema,
   so it is safe in the window where migrations are not.

## 9. The cheaper variant, considered and rejected

Set `users.id = parse_or_hash_uuid(old_sub)` for existing users and a random UUID for new ones.
`configs`, `drawings` and `devices` then need no rewrite at all — only the TEXT tables narrow —
and the JSONB drawing blobs are never touched.

Rejected. It leaves every existing user with a publicly computable id permanently, which is the
derivation note's section 2 preserved rather than fixed, and it makes the invariant untestable:
half the ids would be random and half derived, so no test can assert that ids are opaque. The
saving scales with the size of `drawings`, which at internal-testing volume is small. Worth
re-checking that assumption against the real table size before the freeze; it is not expected to
change the answer.

## 10. Not doing: the teddy.fyi side

`teddy-fyi-api-rust` keeps raw Google subjects after the split. One household, one provider, no
published policy, and the grocery/todo tables carry the subject in `"userId"`/`"ownerId"` columns
throughout. Divergence between the two repos is the point of splitting, not a debt to repay.

Two things stay true there and are worth remembering rather than rediscovering: the raw subject
still leaks to co-members of a shared grocery list through `grocery_list_members`, and
`join_handler` still embeds it in membership row ids. Both are documented in the derivation note.
If the grocery iOS app ever needs Sign in with Apple, this note applies to it unchanged.

## 11. Forward notes for the Apple work

Not part of this migration. Recorded so the schema above is not re-litigated when it happens.

* Apple's `sub` is stable and scoped to the developer **team**, so it is consistent across our own
  apps — the same property Google's has, and what makes `(provider, subject)` a sound key.
* The client secret is itself a JWT signed with a `.p8` key and capped at six months. It expires
  silently and takes sign-in down when it does. Automate the rotation or diarise it; this is the
  most common operational failure of Sign in with Apple.
* Name and email arrive **only on the first authorization**. Persist on insert or lose them; the
  user's only recovery is removing the app from their Apple ID settings.
* Validation differs from Google's: Apple's JWKS, `iss = https://appleid.apple.com`, `aud` the
  client/bundle id. `login_handler` currently has one Google path and one flat audience set built
  by `load_google_client_ids`; a second provider needs a per-provider verifier and per-provider
  audiences, chosen by a `provider` field on `LoginRequest`, not a widened flat set.
* `/auth/device/claim` takes a Google ID token from the parent's browser and will need the same
  provider tagging.
